**Compiled:** 2026-09-19 · **Scope:** (A) observability for MCP servers, (B) testing & conformance for MCP servers
**Method:** primary sources only (spec pages, OTel semconv repos, GitHub repos/releases, package registries, vendor docs/blogs). GitHub REST API was unauthenticated and intermittently rate-limited; registry APIs (npm/PyPI) and `raw.githubusercontent.com` were used instead where possible.

# AREA A — Observability for MCP servers

## A1. Official OpenTelemetry semantic conventions for MCP / GenAI

### A1.1 Is there an official `mcp.*` semconv namespace?

**Yes — but it is `Development` (experimental), unreleased in its new home, and the registry page on `opentelemetry.io` is a deprecation stub.**

The namespace today has exactly **four** attributes (source: <https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/registry/attributes/mcp.md>, branch `main`, retrieved 2026-09-19):

| `mcp.method.name` | **Development** | string | The name of the request or notification method | `notifications/cancelled`; `initialize`; `notifications/initialized` |

### A1.4 Status of `gen_ai.*` attributes

**`Development`** — not stable, not even release-candidate. Evidence from the live registry docs (retrieved 2026-09-19):

- Every `gen_ai.*` attribute in the MCP client/server span tables is badged `Development` (`mcp.md`, lines ~120–350).
- The GenAI inference span (`docs/gen-ai/gen-ai-spans.md`) is badged **Status: Development**; `gen_ai.operation.name` and `gen_ai.provider.name` are `Required` but `Development`.
- Only *referenced* attributes from the core registry are stable: `error.type` (Stable), `server.address`/`server.port` (Stable), `network.*` (Stable), `client.address`/`client.port` (Stable). `rpc.response.status_code` is **Release Candidate**.

**Practical consequence:** you cannot pin a stable semconv schema URL for MCP today. The C# SDK still names its instruments `Experimental.ModelContextProtocol` — consistent with this.

### A1.5 Span conventions (new repo, `docs/gen-ai/mcp.md`)

Two span types, both `Development`, requirement level **Recommended**:

| Span | Kind | Name format |
|---|---|---|
| MCP client span (type `mcp.client`) | `CLIENT` | `{mcp.method.name} {target}`, target = `{gen_ai.tool.name}` or `{gen_ai.prompt.name}`; falls back to `{mcp.method.name}` |
| MCP server span (type `mcp.server`) | `SERVER` | same rule |

Key normative rules quoted:
- *"MCP tool call execution spans are compatible with GenAI [execute_tool spans]. If the MCP instrumentation can reliably detect that outer GenAI instrumentation is already tracing the tool execution, it SHOULD NOT create a separate span. Instead, it SHOULD add MCP-specific attributes to the existing tool execution span."*
- *"Instrumentation MAY allow users to opt into including `{mcp.resource.uri}` as `target` … but SHOULD NOT include it by default to avoid high cardinality span names."*
- `error.type`: *"When `CallToolResult` is returned with `isError` set to `true`, this attribute SHOULD be set to `tool_error`."*
- Client-span `Required` attribute: `mcp.method.name`. Server-span additionally has `client.address`/`client.port` as Recommended.
- `network.transport`: *"SHOULD be set to `tcp` or `quic` if the transport protocol is HTTP. It SHOULD be set to `pipe` if the transport is stdio."*

**Transport inference table** (from the same doc, section "Recording MCP transport"):

| MCP transport | `network.transport` | `network.protocol.*` | `mcp.protocol.version` |
|---|---|---|---|
| stdio | `pipe` | — | any |
| Streamable HTTP | `tcp`/`quic` | `http` / `2` | `2025-06-18` or newer |
| HTTP with SSE | `tcp`/`quic` | `http` / `1.1` or `2` | `2024-11-05` or older |
| Custom: websockets | `tcp` | `websocket` | any |

### A1.6 Context propagation (semconv side)

From the same doc, section "Context propagation":
- *"Instrumentations SHOULD propagate context using the configured OpenTelemetry propagators by injecting it into the MCP request `params._meta` property bag … The receiver extracts the context from `params._meta` and uses it as the remote parent."*
- *"Although the MCP convention expects keys in `params._meta` to be DNS-prefixed, the context propagation keys SHOULD be written unprefixed. SEP-414 defines this explicit handling for the W3C Trace Context and Baggage keys (`traceparent`, `tracestate`, and `baggage`)."*
- *"MCP server instrumentation SHOULD, by default, use context extracted from MCP `params._meta` as a parent for MCP server span and SHOULD link current ambient context, if it's present."*
- Explicit note: *"MCP and underlying transport (such as HTTP) contexts are independent. One MCP request can be served by multiple HTTP requests (for example, because of retries) and one streamable HTTP request can serve more than one MCP request/notification."*

### A1.7 📊 Recommended metrics — exact names (this answers A5's "official metric names")

**Four official MCP metrics**, all `Histogram`, unit `s` (seconds), stability `Development`, requirement level Recommended (source: new-repo `docs/gen-ai/mcp.md`, retrieved 2026-09-19):

| Metric | Instrument | Unit | Description |
|---|---|---|---|
| `mcp.client.operation.duration` | Histogram | `s` | Duration of the MCP request or notification **as observed on the sender**, from send until response/ack |
| `mcp.server.operation.duration` | Histogram | `s` | MCP request/notification duration **as observed on the receiver**, from receipt until result/ack sent |
| `mcp.client.session.duration` | Histogram | `s` | Duration of the MCP session as observed on the MCP client |
| `mcp.server.session.duration` | Histogram | `s` | Duration of the MCP session as observed on the MCP server |

**All four SHOULD use** `ExplicitBucketBoundaries = [0.01, 0.02, 0.05, 0.1, 0.2, 0.5, 1, 2, 5, 10, 30, 60, 120, 300]`.

`mcp.client.operation.duration` / `mcp.server.operation.duration` attributes:
- `Required`: `mcp.method.name`
- `Conditionally Required`: `error.type`, `gen_ai.prompt.name`, `gen_ai.tool.name`, `rpc.response.status_code`
- `Recommended`: `gen_ai.operation.name` (set to `execute_tool` for tool calls), `jsonrpc.protocol.version`, `mcp.protocol.version`, `network.protocol.name`, `network.protocol.version`, `network.transport`, `server.address`, `server.port`
- `Opt-In`: `gen_ai.prompt.variable`, `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`

`mcp.{client,server}.session.duration` attributes: `error.type` (cond. required), `jsonrpc.protocol.version`, `mcp.protocol.version`, `network.protocol.name`, `network.protocol.version`, `network.transport` (sessions metrics carry **no** `server.address`/`server.port`).

**🚩 Explicit conflicts / gaps to flag:**

1. **There is NO metric literally named "tool call duration".** Tool-call latency is derived from `mcp.{client,server}.operation.duration` filtered by `mcp.method.name = "tools/call"` (plus `gen_ai.tool.name`). Vendor dashboards that advertise a "tool call duration" metric are doing this filtering or using a non-semconv instrument.
2. **There is NO `mcp.*` request-count / error-rate counter metric in the conventions.** Request counts come from the histogram's `_count` series; error rate comes from `error.type` / `rpc.response.status_code` on the histogram.
3. **Token usage is NOT in the `mcp.*` namespace.** It lives in `gen_ai.usage.*` (`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, plus per-modality `gen_ai.usage.{text,image,audio}.input_tokens`, `*_cache_read.input_tokens`, and `gen_ai.usage.reasoning.output_tokens`) on GenAI inference spans — source <https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-spans.md>, retrieved 2026-09-19. An MCP server by itself does not call a model, so it has no token usage to report; token metrics belong to the client/agent side.
4. **`mcp.session.id` is semantically strained by the 2026-07-28 revision**, which *removed protocol-level sessions and the `Mcp-Session-Id` header* (see §A3). The semconv description still links to the `2025-06-18` session-management spec section. Flag as an unresolved inconsistency between semconv `main` and spec `2026-07-28`.

## A2. SEP-414 — OpenTelemetry trace context propagation in `_meta`

Source: <https://modelcontextprotocol.io/seps/414-request-meta.md> (retrieved 2026-09-19). Status **Final**, type **Standards Track**, **Created 2025-04-25**, author Adrian Cole ([@codefromthecrypt](https://github.com/codefromthecrypt)), sponsor Marcelo Trylesinski ([@Kludex](https://github.com/Kludex)), PR [#414](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/414).

**Exactly what is specified** (the SEP adds *documentation* to the MCP spec — no new wire behaviour):

1. When OTel trace context is propagated via `_meta`, the keys **`traceparent`**, **`tracestate`**, and **`baggage`** follow [W3C Trace Context](https://www.w3.org/TR/trace-context/) and [W3C Baggage](https://www.w3.org/TR/baggage/) value formats.
2. A non-normative example showing trace context in `_meta`.
3. A note clarifying **why this is an exception to DNS-prefixing keys in `_meta`**: to remain compatible with existing implementations and the OpenTelemetry semantic conventions.

**Non-normative example from the SEP:**
```json
{
  "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" },
    "_meta": { "traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01" }
  }
}
```

**Rules for clients and servers** — the SEP itself does not state MUST/MUST NOT for client vs server. The normative-ish rules live in the semconv doc (quoted in §A1.6): instrumentations **SHOULD** inject context into `params._meta` when creating a request or notification; the receiver **SHOULD** extract it and use it as the remote parent; servers **SHOULD** link the ambient context if present. The SEP's stated risk if this is not documented uniformly: *"differing interpretations could materialize, such as namespacing traceparent like `io.modelcontextprotocol.traceparent`, which will break traces and log correlation."*

**Rationale / prior art:** the pattern was *already* in practice before the SEP — C# SDK instrumentation, Python SDK PR #1693, OpenInference MCP instrumentation (Python + TypeScript), Envoy AI Gateway, Pydantic Logfire, ToolHive (stacklok).

**Related SEPs:** SEP-1788 (reserved keys in `_meta`; should be updated with `traceparent`/`tracestate`/`baggage`), SEP-2028 (forwarding `_meta` values to HTTP headers).

**Backward compatibility:** explicitly backward compatible (documents existing conventions).
**Security:** *"Trace context in `_meta` may include correlation IDs. Implementations should follow existing data-handling guidance appropriate to their environment."*

**Confirmed landed in the spec:** the 2026-07-28 changelog lists under *Minor changes*: *"Document OpenTelemetry trace context propagation conventions for `_meta` keys (`traceparent`, `tracestate`, `baggage`) (SEP-414)."* — <https://modelcontextprotocol.io/specification/2026-07-28/changelog.md>, retrieved 2026-09-19.

**Note the equivalent ACP change:** <https://github.com/agentclientprotocol/agent-client-protocol/pull/297>.

## A3. The MCP spec's own deprecation guidance

### A3.1 What was deprecated

**SEP-2577 — "Deprecate Roots, Sampling, and Logging"**, status **Final**, Standards Track, **Created 2026-04-14**, author Kurtis Van Gent ([@kurtisvg](https://github.com/kurtisvg)), PR [#2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577). Source: <https://modelcontextprotocol.io/seps/2577-deprecate-roots-sampling-and-logging.md> (retrieved 2026-09-19).

Deprecated core protocol features:
- **Roots** — `roots/list`, `notifications/roots/list_changed`, and types `Root`, `ListRootsRequest`, `ListRootsResult`, `ListRootsResultResponse`, `RootsListChangedNotification`, plus `ClientCapabilities.roots`.
- **Sampling** — `sampling/createMessage`, `ClientCapabilities.tasks.requests.sampling`, and 11 types (`CreateMessageRequest*`, `CreateMessageResult*`, `SamplingMessage`, `SamplingMessageContentBlock`, `ToolChoice`, `ToolUseContent`, `ToolResultContent`, `ModelPreferences`, `ModelHint`).
- **Logging** — `logging/setLevel`, `notifications/message`, `ServerCapabilities.logging`, and types `LoggingLevel`, `SetLevelRequest*`, `SetLevelResultResponse`, `LoggingMessageNotification*`.

Deprecation rationale for Logging, verbatim: *"Overlapping infrastructure: Standard logging mechanisms (stderr for stdio transports, OpenTelemetry for structured observability) are mature, widely adopted, and better suited to logging than an application-protocol channel."* Adoption evidence cited: the [feature support matrix](https://modelcontextprotocol.io/clients#feature-support-matrix) and [discussion #2536](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/2536).

**During the deprecation window: no wire-level changes.** No types removed, no capability-negotiation change, no existing implementation breaks. Implementations **SHOULD** still declare the capabilities and **MUST** still handle them correctly. *"Implementations SHOULD emit a warning (e.g., in logs or developer tooling) when deprecated capabilities are negotiated."* New implementations **SHOULD NOT** add support.

Source: <https://modelcontextprotocol.io/specification/2026-07-28/deprecated.md> (retrieved 2026-09-19):

| Feature | Deprecation SEP | Deprecated in | Migration path | Earliest removal |
|---|---|---|---|---|
| Roots | SEP-2577 | `2026-07-28` | Pass directories or files via tool parameters, resource URIs, or server configuration | First revision released on or after **2027-07-28** |
| Sampling | SEP-2577 | `2026-07-28` | Integrate directly with LLM provider APIs | First revision released on or after **2027-07-28** |

**Removed section: "No features have been removed under this policy yet."**

### A3.3 Minimum deprecation window (feature lifecycle policy)

Source: <https://modelcontextprotocol.io/community/feature-lifecycle.md>, adopted via **SEP-2596** (retrieved 2026-09-19).

- Three feature states: **Active**, **Deprecated**, **Removed**.
- *"Specify the **minimum deprecation window**: the number of months, **at least twelve**, that the feature must remain Deprecated before it is eligible for removal. The window is measured from the release of the specification revision in which the feature is first marked Deprecated, **not** from the date the SEP reaches Final."*
- Earliest removal = *"the first specification revision released as Current on or after the window elapses."*
- **Expedited removal:** the twelve-month floor *"may be shortened when the feature presents an active security risk, meaning a vulnerability with a published security advisory or documented in-the-wild exploitation for which no in-place mitigation exists."* Requires Core Maintainer approval, and *"must still provide at least **ninety days** between the feature becoming Deprecated and its earliest removal."*
- **Tier 1 SDK obligations** once the deprecating revision is Current: mark the API surface deprecated via the language's native mechanism (`@Deprecated` Java, `[Obsolete]` .NET, `@deprecated` JSDoc TS, `Deprecated:` Go doc convention) in the next release, and *should* emit a runtime warning when the feature is exercised. Non-compliance risks [Tier Relegation](https://modelcontextprotocol.io/community/sdk-tiers#tier-relegation).
- Removal from the spec does **not** oblige an SDK to drop the feature; that is governed by the SDK's own revision-support policy.

**So: minimum window = 12 months from 2026-07-28 → earliest removal 2027-07-28, matching the registry.**

### A3.4 🚩 Important nuance — `logging/setLevel` was *removed*, Logging was *deprecated*

These are two different things and are easy to conflate:

- The **Logging feature** (`notifications/message` + the `logging` server capability) is **Deprecated** but still in the spec through the window.
- **`logging/setLevel` as a method was REMOVED** in 2026-07-28 as part of the stateless rewrite (SEP-2575). From the changelog, Major change #5: *"Remove `ping`, `logging/setLevel`, and `notifications/roots/list_changed`. Log level is now set per-request via `io.modelcontextprotocol/logLevel` in `_meta`; servers **MUST NOT** emit `notifications/message` for requests that did not include this field."*

Consequence: on a 2026-07-28 connection, a server that still wants to emit protocol logs must read `io.modelcontextprotocol/logLevel` from each request's `_meta`; there is no session-level control. The logging spec page confirms: per-request `io.modelcontextprotocol/logLevel`; `notifications/message` is **request-scoped** and *"the server MUST NOT deliver it on a `subscriptions/listen` stream or on any stream other than the one carrying the response to the request that set the log level."* Invalid log-level values → `-32602` (Invalid params); internal errors → `-32603`.

### A3.5 🚩 Source conflict: SEP-2577's own text vs. the final policy

SEP-2577 (Final, preserved as a historical record) says the features are *"deprecated starting in the specification version that includes this SEP (**expected June 2026**)"* and describes a *"one-year-per-version support policy proposed in a separate SEP"* where *"each of those subsequent versions will in turn support the features for one year after its own release."*

The **actual** adopted policy (SEP-2596, `/community/feature-lifecycle`) is a **single 12-month window measured from the release of the revision that first marked the feature Deprecated**, with a 90-day expedited floor — **not** a rolling one-year-per-version scheme. The SEP's "expected June 2026" also slipped to the 2026-07-28 revision. **Treat the lifecycle policy page as authoritative; SEP-2577's timeline prose is superseded.**

## A4. What should an MCP server log to stderr on stdio transport?

Source: <https://modelcontextprotocol.io/docs/2026-07-28/tools/debugging.md> (retrieved 2026-09-19).

**Official guidance, quoted:**

- *"When building a server that uses the local stdio transport, all messages logged to stderr (standard error) will be captured by the host application automatically."*
- ⚠️ *"Local MCP servers should not log messages to stdout (standard out), as this will interfere with protocol operation."*
- For Streamable HTTP: *"stderr is not captured by the client. Use your own server-side log aggregation or OpenTelemetry for logs, and standard HTTP tooling (curl, browser DevTools Network panel) to inspect requests and SSE streams."*
- Logging over the protocol (`notifications/message`) is *"deprecated as of protocol version `2026-07-28`."*

**What to log** — the spec's own "Important events to log" list: *Startup steps · Resource access · Tool execution · Error conditions · Performance metrics.*

**Best-practice section (official):**
- Structured logging: *"Use consistent formats · Include context · Add timestamps · Track request IDs."*
- Error handling: *"Log stack traces · Include error context · Track error patterns · Monitor recovery."*
- Performance tracking: *"Log operation timing · Monitor resource usage · Track message sizes · Measure latency."*
- Sensitive data: *"Sanitize logs · Protect credentials · Mask personal information."*

**Severity levels** if you still emit protocol logs (RFC 5424, from the logging spec page): `debug`, `info`, `notice`, `warning`, `error`, `critical`, `alert`, `emergency`.

**Hard security requirements from the logging spec** (`/specification/2026-07-28/server/utilities/logging.md`): log messages **MUST NOT** contain credentials or secrets, personal identifying information, or *"internal system details that could aid attacks."* Implementations **SHOULD** rate-limit messages, validate all data fields, control log access, and monitor for sensitive content.

**🚩 Not verified:** I found **no official MCP-published structured-log *schema*** (no JSON field names, no required keys) for stderr logging. The official guidance is prose-level only. Any claim of a canonical MCP stderr JSON schema should be treated as unverified.

### A5.2 Sentry — MCP Monitoring (the most concrete vendor spec found)

Primary docs: <https://docs.sentry.io/product/mcp-servers/getting-started.md> (retrieved 2026-09-19; no explicit last-updated date visible on the page).
Design spec: <https://raw.githubusercontent.com/getsentry/sentry-docs/6c602f63f9526821f012fb1633b878e6e9b64f23/develop-docs/sdk/expected-features/mcp-instrumentation/tracing.mdx> (commit-pinned, retrieved 2026-09-19).
Blog: <https://sentry-blog.sentry.dev/introducing-mcp-server-monitoring/> (retrieved 2026-09-19; no date visible in the extracted body).

**Version requirements (exact):**
- JavaScript: MCP Monitoring requires **Node SDK `9.46.0`+**. Stable `@modelcontextprotocol/server` **2.x** support requires Sentry JS SDK **`10.70.0`+**. `recordInputs`/`recordOutputs` require **`10.33.0`+**. Cloudflare stream mode requires `@sentry/cloudflare` **`10.49.0`+**.
- Python: MCP Monitoring requires **`sentry-sdk` `2.43.0`+**.

**API:** JS — `Sentry.wrapMcpServerWithSentry(new McpServer({...}))`. Python — `integrations=[MCPIntegration()]` from `sentry_sdk.integrations.mcp`. Supports the MCP Python SDK (low-level **and** FastMCP) plus standalone FastMCP.

**Sentry span names/ops and attributes** (their own doc; they state they follow the draft OTel MCP semconv *"as closely as possible, with some opinionated additions"*):
- Span op MUST be `"mcp.server"`; notifications use `"mcp.notification.client_to_server"` / `"mcp.notification.server_to_client"`.
- Span names: `tools/call {mcp.tool.name}`, `prompts/get {mcp.prompt.name}`, `resources/read {mcp.resource.uri}`, `initialize`, or the raw notification method name.

## A6. Official MCP SDK support for OpenTelemetry

### A6.1 Python SDK — ✅ **native, built-in, on by default**

- Package: **`mcp`** on PyPI, current version **2.2.0**, released **2026-09-07** (PyPI JSON API, retrieved 2026-09-19). Repo: <https://github.com/modelcontextprotocol/python-sdk> (24,340 stars, MIT, last push 2026-09-19).
- **Official docs page: <https://py.sdk.modelcontextprotocol.io/run/opentelemetry/>** (retrieved 2026-09-19).

Quoted facts from that page:
- *"Every server you create emits an OpenTelemetry span for every message it handles. You didn't write that, and you don't import it. It is there the moment you call `MCPServer(...)`."* Same for the low-level `Server`.
- *"Every inbound message becomes a `SERVER` span named after the method and its target. So a `tools/call` for `search_books` is the span `tools/call search_books`, and a bare `tools/list` is just `tools/list`."*
- Attributes: **`mcp.method.name`** and **`mcp.protocol.version`** on every span; **`jsonrpc.request.id`** on requests. A raising handler, or a tool result with `is_error=True`, sets span status to error.

- Disable: remove the `OpenTelemetryMiddleware` from `mcp._lowlevel_server.middleware`. Note the docs explicitly warn the import path is **provisional** (`mcp.server._otel`, leading underscore) and *"something you should expect to change."*
- Logfire is named as a supported backend: `pip install logfire`, `logfire.configure()`.

**Note:** SEP-414 lists *"Python SDK instrumentation"* PR <https://github.com/modelcontextprotocol/python-sdk/pull/1693> as a reference implementation — that PR is the origin of this native support.

## A7. Content-capture / privacy guidance in GenAI semconv

Source: <https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-spans.md>, section **"Capturing instructions, inputs, and outputs"** (retrieved 2026-09-19). Status: Development.

### Are prompts/results captured by default?

**No.** Verbatim: *"Model instructions, user messages, and model outputs are considered sensitive and are often large in size. … **OpenTelemetry instrumentations SHOULD NOT capture them by default, but SHOULD provide an option for users to opt in.**"*

Three sanctioned patterns, in the spec's own order:
1. **[Default] Don't record instructions, inputs, or outputs.**
2. Record them on GenAI spans via `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages` — *"best suited for situations where telemetry volume is manageable and either privacy regulations do not apply or the telemetry storage complies with them, for example, in pre-production environments."*
3. *"Store content externally and record references on the spans"* — *"recommended in production environments where telemetry volume is a concern or sensitive data needs to be handled securely."*

### Which attributes are opt-in (exact, per the MCP + GenAI span tables)

On **MCP client and server spans**:
- `gen_ai.tool.call.arguments` — `Opt-In` — ⚠️ *"This attribute may contain sensitive information."*
- `gen_ai.tool.call.result` — `Opt-In` — ⚠️ same warning
- `gen_ai.prompt.variable` (i.e. `gen_ai.prompt.variable.<argument_name>`) — `Opt-In` — ⚠️ *"This attribute may contain sensitive information."*

On **GenAI inference spans**: `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions`, `gen_ai.prompt.variable` — all `Opt-In`. `gen_ai.output.messages` carries: *"This attribute is likely to contain sensitive information including user/PII data."*

On the **memory span**: `gen_ai.memory.query.text` and `gen_ai.memory.records` — *"Instrumentations SHOULD NOT capture this attribute by default. Capture SHOULD be gated by an explicit user opt-in, for example `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`."* (`gen_ai.memory.records`: *"likely to contain sensitive information including user/PII data"*.)

### The opt-in flag

**🚩 Precise status:** `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` is given in the semconv text as **an example of an opt-in mechanism**, not as a semconv-normative environment variable name: *"Capture SHOULD be gated by an explicit user opt-in, **for example** `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`."* The semconv does not standardize the flag; individual instrumentations choose. (It is the de-facto name used by `opentelemetry-instrumentation-*` GenAI packages.)

### Additional capture mechanics

- **Size/shape:** *"It may contain media, and even in the text form, it may be larger than observability backend limits for telemetry envelopes or attribute values."* Structured attribute values follow JSON schemas (`gen-ai-input-messages.json`, `gen-ai-output-messages.json`, `gen-ai-tool-call-arguments.json`, `gen-ai-tool-call-result.json`). If a language cannot record structured attributes on spans, values **SHOULD** be serialized to JSON strings on spans and recorded structured on events.
- **Truncation:** *"Instrumentation MAY provide a configuration option allowing to truncate properties such as individual message contents, preserving JSON structure."*
- **External-storage hooks:** instrumentations MAY support user-defined in-process hooks, which **SHOULD** be invoked *"regardless of the span sampling decision"* and **independently of the opt-in flags**. The hook receives the structured objects *before* JSON serialization plus the span instance, and MAY modify them. If span attributes are also enabled, they **SHOULD** be recorded *after* the hook, reflecting hook modifications.
- **Cardinality caution for tool definitions:** *"Since this attribute could be large, it's NOT RECOMMENDED to populate non-required properties by default."*
- **Not-yet-done:** `### Streaming chunks` is literally `TODO` in the spec.

### MCP's own privacy requirements for logs (apply to whatever you emit)

From the logging spec: logs **MUST NOT** contain credentials/secrets, PII, or attack-useful internal details; implementations **SHOULD** rate-limit, validate, control access, and monitor for sensitive content.

### Vendor divergence

Sentry gates content with `recordInputs` / `recordOutputs`, which **default to `dataCollection.genAI.inputs` / `dataCollection.genAI.outputs`**, and *"In Sentry JavaScript SDK 10.x, when `dataCollection` isn't configured, this follows `sendDefaultPii`."* So on Sentry JS 10.x with `sendDefaultPii: true`, MCP tool arguments/results are captured **by default** — a different default from the OTel semconv. Their Python quickstart likewise notes `send_default_pii=True` *"to capture tool call arguments and results in Sentry, which may include PII."*

### SEP-2484 — the process rule that produces these tests

<https://modelcontextprotocol.io/seps/2484-conformance-tests-required-for-final-seps.md> — status **Final**, type **Process**, **Created 2026-03-27**, author Paul Carleton ([@pcarleton](https://github.com/pcarleton)), sponsor: none, PR [#2484](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2484).

- Adds a conformance requirement to the **`Accepted → Final`** transition for **Standards Track** SEPs that change **observable protocol behavior** (wire-visible messages, transport-observable side effects — HTTP status codes, headers, connection lifecycle, OAuth redirects — or process-observable stdio/exit-code side effects).
- **Exempt:** Process SEPs, Informational SEPs, Standards Track SEPs with no observable protocol behavior.
- Requires (1) a conformance scenario tagged with the SEP number merged into the conformance repo, targeting the **draft** spec-version tag; (2) a **traceability file** `sep-NNNN.yaml`; (3) the scenario passes against the SEP's reference implementation.
- Traceability file maps every MUST/MUST NOT/SHOULD/SHOULD NOT (and RFC 2119 equivalents SHALL/REQUIRED/RECOMMENDED) to a check **or** a documented exclusion. Checks for **SHOULD-level requirements report as warnings, not failures**. MAY requirements need no row. Exclusions are either *framework gaps* (must link a tracking issue) or *not protocol-observable* (reason only).
- **Spec text is authoritative:** *"Where a test and the spec disagree, the spec is authoritative and the test is a bug."*
- **Not retroactive.** Supersedes **SEP-1627** (whose golden-trace approach was dropped in favour of the scenario-and-checks model).
- **Disputes:** a `disputed` label is applied by a conformance maintainer; disputed tests don't affect SEP-1730 tier assessments until resolved; escalation to Core Maintainers is available.
- **Tiering stability:** SEP-1730 tier assessments run against a **pinned conformance release**, not repo tip.
- **Authorship:** *"Scenarios are authored in TypeScript"*; the **sponsor** is responsible for ensuring one is written.
- SEP-2484's own prerequisites for Final included a traceability-file format + schema, a scaffolding tool (`npx @modelcontextprotocol/conformance new-scenario --sep <number>`), draft-version-tag support in the harness, and a published `MAINTAINERS.md`.

Reference-implementation scenarios already following this pattern: `JsonSchema2020_12Scenario` (SEP-1613), `ElicitationDefaultsScenario` (SEP-1034), `ServerSSEPollingScenario` (SEP-1699), `ElicitationEnumsScenario` (SEP-1330).

| **Web** | `npx @modelcontextprotocol/inspector` | Full graphical inspector in the browser; the default |
| **CLI** | `npx @modelcontextprotocol/inspector --cli` | Scriptable, machine-readable for CI/shell/agents |
| **TUI** | `npx @modelcontextprotocol/inspector --tui` | Interactive terminal UI |

*"All three are built on the same shared core, so a connection behaves identically across them: the same transports, the same configuration files, the same OAuth state on disk, and the same protocol-era negotiation."* **Requires Node 22.19.0 or newer.**

`mcp-inspector` is a **thin launcher** owning only the mode flag (`--web`/`--cli`/`--tui`; at most one — passing two errors with `Specify at most one of --web, --cli, or --tui.`) and `-h`/`--help`. *"Mode flags are recognized only at the front of the command line: the first token that isn't `--web`/`--cli`/`--tui` ends launcher parsing."* Everything else (`--catalog`, `--config`, `--server-url`, `--transport`, `--method`, OAuth flags) is owned by the client, and the clients do not all define the same set.

### Running against a stdio server

```bash
npx @modelcontextprotocol/inspector node path/to/server/index.js
npx @modelcontextprotocol/inspector --tui node path/to/server/index.js
npx @modelcontextprotocol/inspector --cli node build/index.js --method tools/list
npx -y @modelcontextprotocol/inspector npx @modelcontextprotocol/server-filesystem ~/Desktop
npx @modelcontextprotocol/inspector uvx mcp-server-git --repository ~/code/mcp/servers.git
```
The web command *"prints a URL containing a one-time session token; open it in your browser."*

### Running against a Streamable HTTP server

```bash
npx @modelcontextprotocol/inspector --server-url https://api.example.com/mcp --transport http
npx @modelcontextprotocol/inspector --cli https://api.example.com/mcp --transport http --method tools/list
mcp-inspector --cli <server> --method tools/call --tool-name get_weather --tool-arg city=Boston --format json | jq .result
```

### Methods the CLI supports

`initialize`, `tools/list`, `tools/call` (`--tool-name`, `--tool-arg`/`--tool-args-json`), `resources/list`, `resources/read` (`--uri`), `resources/templates/list`, `prompts/list`, `prompts/get` (`--prompt-name`, `--prompt-args`), `logging/setLevel` (`--log-level`, **legacy era only**), `servers/list` and `servers/show` (read the catalog **without connecting**). Stream- or session-only methods (e.g. `logging/tail`) are rejected.

One request per run: *"Each CLI run connects to a server, invokes the single request you name with `--method`, prints the result, and exits."*

**Argument coercion:** `--tool-arg key=value` **JSON-parses** values (`count=1` → number 1; `"012"` → `12`). `--tool-args-json` passes the whole object **verbatim** with no coercion. The two are mutually exclusive.

### Output formats and exit codes (the CI contract)

- `--format text` (default) pretty-prints for humans.
- `--format json` emits **a single JSON object on stdout with no banners**, so the whole output pipes cleanly: `... --format json | jq '.result.tools[].name'`.
- `--app-info` probes whether a tool ships an MCP App UI **without calling the tool**; `tools/list --app-info` always emits **NDJSON** (one line per tool) regardless of `--format`.

| Exit code | Meaning |
|---|---|
| `0` | Success |
| `1` | Usage or unexpected error (catch-all) |
| `2` | No MCP App found on the tool (`--app-info` probe) |
| `3` | Server requires authentication (401/403, `WWW-Authenticate`, OAuth) |
| `4` | Server unreachable (DNS, connection refused, timeout, `fetch failed`) |
| `5` | Tool error: `tools/call` returned `isError: true`, **or the tool wasn't found** |

On any non-zero exit the CLI also writes **a single JSON line to stderr**:
```json
{"error":{"code":"auth_required","message":"Unauthorized","status":401,"url":"https://api.example/mcp"}}
```
Parseable with `2>&1 | tail -1 | jq .error`. *"A `tools/call` that returns `isError: true` still prints its payload, but exits `5`, so an `&&` chain doesn't proceed on a failed call."*

### CI recipe (official)

```bash
set -euo pipefail
mcp-inspector --cli --config ./ci-servers.json --server my-server \
  --stored-auth-only --method tools/list --format json \
  | jq -e '.result.tools | map(.name) | index("get_weather")' > /dev/null
```
- **`--stored-auth-only`**: never start interactive OAuth or step-up, never auto-open a browser; use tokens from the shared store if present, otherwise fail immediately with `auth_required`. *"This is the flag CI wants."*
- **`--use-stored-auth`**: reuse a token the web Inspector already obtained on this machine, refreshing it first.
- Without either, and with no TTY on stdin/stderr, the CLI **fails fast** with `auth_required` rather than hanging on a callback.

Branch on failure class:
```bash
if out=$(mcp-inspector --cli "$URL" --transport http --method tools/list 2>err.json); then
  echo "$out"
else
  case $? in
    3) echo "needs auth: run the web inspector once to sign in" ;;
    4) echo "server unreachable" ;;
    *) jq .error < err.json ;;
  esac
fi
```

**Roots caveat:** *"The config file is the only durable way to give a run its roots: there is no roots flag, and `--method roots/set` applies only to that one short-lived connection."*

**Proxies:** honours `HTTPS_PROXY`/`HTTP_PROXY` (and lowercase) plus `NO_PROXY`; the proxy agent is loaded lazily.

**⚠️ Security note from the docs:** `servers/show` redacts secret-bearing fields (env values, sensitive headers, OAuth client secrets) but does **not** scrub credentials embedded in a server `url` (userinfo or query tokens) or in stdio `args`.

## B5. Protocol-era testing in the Inspector (legacy vs. modern)

Source: <https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector/protocol-eras.md> (retrieved 2026-09-19).

**Core design:** *"The 2026-07-28 revision of MCP made substantial changes to the protocol. The Inspector therefore treats **protocol era** (legacy or modern, meaning before or as of that revision) as a first-class, per-server setting, **orthogonal to the transport**: the same HTTP URL can be inspected as a legacy server or as a modern one."*

**The setting:** each server carries `protocolEra` of `legacy`, `auto`, or `modern`.
- In the **web client**: Server Settings.
- In a **catalog or config file**: the `protocolEra` field.
- In the **CLI and TUI**: from that same file (*"Era selection works the same way in all three clients"*).

| Era | What the Inspector does at connect |
|---|---|
| `legacy` | **The default.** Plain `initialize`, **no probing at all** |
| `auto` | Probe `server/discover` first, fall back to `initialize` on any non-modern outcome |
| `modern` | Pin exactly `2026-07-28`. **No fallback**, so a non-modern server fails loudly |

**Why `legacy` is the default (quoted):** *"A debugging tool must not auto-probe. A `server/discover` probe stalls against silent legacy stdio servers, and it pollutes the recorded transcript you came here to read. Opting into `auto` or `modern` is a deliberate act, so what you see in the Protocol tab is what your server would have seen from a client behaving the way you configured."*

**Post-connect reporting:** the negotiated era appears in the connection header and in **Connection Info**. On a modern connection, `server/discover` also supplies `capabilities` (including `extensions`), `instructions`, and the list of `supportedVersions`. The server's name/version arrive in the result `_meta` under `io.modelcontextprotocol/serverInfo`.

### Behavioural deltas a dual-era test must cover

| Feature | Legacy | Modern (2026-07-28) |
|---|---|---|
| **Logging** | Session-scoped: client sends `logging/setLevel` once; Logs tab shows a **Set Active Level** selector + Set button | `logging/setLevel` is **gone**. Client opts in **per request** via `_meta["io.modelcontextprotocol/logLevel"]`. Logs tab shows **Log Level per Request**. Server **MUST NOT** emit `notifications/message` without the opt-in. Logs ride that request's SSE stream. *"Set the control to Off and the `logLevel` key is omitted entirely, so the same tool call produces no logs at all. That silence is correct behavior, not a bug."* Per-server default is `debug`; `modernLogLevel: "off"` opts back out |
| **Resource subscriptions** | `resources/subscribe`; server emits `notifications/resources/updated` | **`subscriptions/listen`** with a filter carrying `resourceSubscriptions` + `resourcesListChanged`; confirmed by `notifications/subscriptions/acknowledged`. Long-lived stream with a `Connecting...`→`Listening` badge; reconnects by re-sending `subscriptions/listen` |
| **Tasks** | Tab gated on `capabilities.tasks`; `tasks/list` + polling `tasks/get`; blocking `tasks/result`; `Cancel` → `tasks/cancel` | Tasks are an **extension** (`io.modelcontextprotocol/tasks`, SEP-2663), so the tab is gated on the **negotiated extension**. `tools/call` returns a `CreateTaskResult` (`resultType: "task"`). **Poll `tasks/get` only; there is no `tasks/list`.** A completed task **inlines its result** — no blocking `tasks/result`. `input_required` → embedded elicitation in the pending-request modal; answering sends **`tasks/update`** with `inputResponses` |
| **MRTR** | n/a — the legacy `collect_elicitation` pattern (server calling `server.elicitInput`) **errors** on a 2026-07-28 connection *"because server-to-client requests aren't allowed there"* | `tools/call` may return `input_required` embedding an elicitation, sampling request, or `roots/list`; client answers and retries under a **fresh JSON-RPC id** until `complete`. Driven **manually** by the Inspector at the pending-request modal |
| **Sessions** | Legacy Streamable HTTP may carry `Mcp-Session-Id`, torn down with HTTP `DELETE` | *"sessionless and per-request"* — no session id ⇒ **the client SDK sends no `DELETE`**; disconnect is purely local |
| **Errors** | One generic JSON-RPC failure; you read the message to tell cases apart | Typed spec errors: `-32020` `HeaderMismatch` (HTTP 400), `-32021` `MissingRequiredClientCapability` (400), `-32022` `UnsupportedProtocolVersion` (400, supported versions in `data.supported`), `-32601` method not found (404), plus distinct **Unknown Tool** vs **Invalid Parameters** `-32602` error panels |
| **Headers** | — | `Mcp-Method` / `Mcp-Name` required on POST; `x-mcp-header` → `Mcp-Param-*` mirroring (SEP-2243). Invalid header names ⇒ tool is **struck through** under an "Excluded (SEP-2243)" divider, since *"A conforming client MUST drop such a tool from `tools/list`"* |

### Implications for testing a dual-era server

1. **Era is not transport.** One HTTP URL must be testable both ways; your CI matrix needs `protocolEra` as an explicit axis, not a transport axis.
2. **`legacy` default means the Inspector will not discover your modern-only server by accident.** A modern-only server tested with default settings gets a plain `initialize` — which it must still reject cleanly with `-32022` + `data.supported`, not hang.
3. **Silence is correct.** Absent the `io.modelcontextprotocol/logLevel` stamp, a modern server emitting no logs is behaving correctly. A naive test asserting "logs appear" will produce a false failure.
4. **Statelessness breaks naive fixtures.** *"A stateless modern handler constructed per request cannot hold state between calls, which is why `test-servers/configs/subscriptions-modern-http.json`, unlike its legacy counterpart, omits an `update_resource` tool: the mutation would run against a throwaway server instance and be invisible to the next read."*
5. **Reproducible era fixtures ship in the repo** — clone and build:
   ```bash
   git clone https://github.com/modelcontextprotocol/inspector
   cd inspector && npm install && npm run build
   cd clients/web && npm run test-servers:build
   ```
   Named configs: `logging-legacy-http.json`, `logging-modern-http.json`, `subscriptions-legacy-http.json`, `subscriptions-modern-http.json`, `tasks-legacy-http.json`, `tasks-modern-http.json`, `mrtr-showcase-http.json`, `xmcpheader-modern-http.json`, `modern-network-http.json`.
6. **Known Inspector weakness to test around:** *"`Mcp-Param-*` mirroring is skipped by the SDK in the browser. Calling a mirrored tool from the web client omits the header, so a strict server answers `-32020` … The same tool called from the CLI or TUI, which both run on Node, mirrors correctly."* **Mirrored-header conformance must be tested from the CLI/TUI, not the web client.**
7. `mrtr_loop` deliberately *"never completes, so the client stops at its `MRTR_MAX_ROUNDS` limit"* — a ready-made fixture for testing your client's loop guard.

# Summary of things I could NOT verify, or where sources conflict

**Conflicts / inconsistencies:**

1. **Semconv registry location conflict.** `opentelemetry.io/docs/specs/semconv/registry/attributes/mcp/` still serves the `mcp.*` attributes (badged Deprecated, "moved"), while `opentelemetry.io/docs/specs/semconv/gen-ai/` renders as "Moved". The canonical source is now `open-telemetry/semantic-conventions-genai`. Do not cite the old `opentelemetry.io` MCP registry page as current.
2. **No schema URL / no release for the new GenAI repo.** Its README says `## Schema URL` → `TODO`, and its CHANGELOG has no released version. There is no pinnable semconv version for `mcp.*` today.
3. **SEP-2577's timeline prose contradicts the adopted policy.** SEP-2577 says "expected June 2026" and implies a rolling one-year-per-version support window; SEP-2596 / `/community/feature-lifecycle` establishes a single 12-month window (measured from the revision's release) plus a 90-day expedited floor. The policy page is authoritative.
4. **`logging/setLevel` removed vs. Logging deprecated.** Two different actions in the same revision; see §A3.4.
5. **`mcp.session.id` vs. sessionless 2026-07-28.** The semconv still describes sessions and links to the `2025-06-18` transports section, but 2026-07-28 removed `Mcp-Session-Id` and protocol-level sessions.
6. **`mcp-scan` name collision.** PyPI `mcp-scan` → renamed to `snyk-agent-scan`; npm `mcp-scan` 2.0.13 is an unrelated third-party project.
7. **`mcp-eval` name collision.** At least three projects (`lastmile-ai`, `alpic-ai`, `smart-mcp-proxy`) share the name.
8. **Conformance README vs. published versions.** The README documents `--requirements` / `tier-check` / per-check baselines, which are on the **0.2.0-alpha** line; `latest` is **0.1.16 (2026-03-30)**.
9. **Sentry attribute names diverge from OTel semconv** (`mcp.transport`, `mcp.request.id`, `mcp.tool.name`, `mcp.prompt.name`, `mcp.tool.result.*`, `mcp.request.argument.*` are Sentry-specific and not in the OTel `mcp.*` registry).
10. **traceloop instrumentation's default is inverted** vs. semconv: it captures prompts/completions by default (`TRACELOOP_TRACE_CONTENT=false` to disable); semconv says SHOULD NOT capture by default.
11. **Sentry JS 10.x content-capture default** follows `sendDefaultPii` when `dataCollection` is unconfigured — a different default from semconv.
